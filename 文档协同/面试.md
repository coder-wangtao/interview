CRDT（Conflict-free Replicated Data Type，无冲突复制数据类型）是一种分布式数据结构：多台设备各自修改同一份数据，之后按固定规则合并，结果一定收敛到同一个状态，不需要加锁，也不需要中央服务器裁决谁对谁错。
它适合多人同时编辑、离线后再同步的场景，比如协同文档、同步笔记、分布式计数。

为什么不会冲突?
每次修改都设计成可以任意顺序合并。合并操作满足三条性质：
交换律：先合并 A 再合并 B，和反过来一样。
结合律：多份更新分组合并，结果相同。
幂等：同一份更新合并多次，结果不变。

2.1.后端锁，乐观锁，非分布式
后端锁：当一个用户正在修改某份文档时，其他用户的修改请求必须按照一定规则等待，或者在锁冲突时被拒绝。让修改按规则串行执行
乐观锁：允许并发，但检测冲突（我认为冲突不是每次都会发生，因此先允许修改，提交时再检查数据是否已经被别人改过。）
乐观锁核心机制：版本号
假设数据库中保存了下面这条文档记录：
id content version
1001 Hello 1
用户 A 和用户 B 都读取了版本号为 1 的内容。
用户 A 修改为 Hello!。
用户 B 修改为 Say Hello。
如果用户 A 先提交，数据库更新为版本 2。
用户 B 再提交时，如果仍然按照版本 1 更新，就应该失败，而不是覆盖用户 A 的修改。

2.2.OT、CRDT(状态、操作【notion op operation】)算法
OT:当两个用户基于同一个旧版本产生了不同的编辑操作时，需要根据已经发生的其他操作，转换自己的操作，再应用到最新文档上。注意，OT 不是简单地选择谁先提交，而是尽可能保留双方的修改。
CRDT:通过数据结构和操作规则的设计，让多个副本即使在不同时间、不同顺序下接收更新，在满足相应条件后也能收敛到一致的状态。
OT 的重点是“如何转换操作”。
CRDT 的重点是“如何设计数据结构和操作，使并发修改能够合并”。

CRDT:
State：状态 State 表示文档当前是什么样子。
{
"documentId": "doc-1001",
"content": "Hello!",
"version": 5
}
Operation：操作 Operation 表示用户做了什么。
{
"type": "insert",
"id": "A:12",
"position": 5,
"text": "!"
}

状态型 CRDT（State-based CRDT）
它的思路是：每个副本维护自己的状态，通过交换状态并执行合并操作，让不同副本最终收敛。
State 副本的内部状态的类型
state_zero 内部状态的初始值
≤ 定义了 state 之间的顺序
update(s，u)定义 state 的更新方式
merge(s，s')函数可以用于合并两个状态得到新状态
副本之间通过传递自己的 state，并进行 merge 操作来达到一致性

操作型 CRDT（Operation-based CRDT）
用户不必每次传输完整状态，而是将编辑操作发送给其他副本，再按照 CRDT 定义的规则应用这些操作。
state 是每个副本的内部状态
state_zero 内部状态的初始值
op 是每个原子操作的类型，副本直接通过传递op来达到同步
apply_op(state，op)是在一个 state 上应用 op 的函数，返回新的状态;op 的交换律指的就是 apply_op(apply_op(state,opA),pB)=apply_op(apply_op(state，opB)，opA)
check_state(state，op)确认一个状态是否满足应用op的前置条件
op-based CRDT 的每一个操作 op 都有对应的前置状态检査函数 check_state，在应用 op 之前需要检查 check_state 函数是否满足，如果不满足就将阻塞延迟。
check_state 函数的目的是为了保证 op 所依赖的因果顺序成立，例如删除 x 节点的操作依赖于 x 节点被创建的操作，否则就无法应用该操作。这也意味着op-based CRDT 的使用者有责任证明每个操作的前置状态都是能够得到满足的
副本之间通过传递彼此缺失的 op，并进行 apply_op 来达到最终一致性
